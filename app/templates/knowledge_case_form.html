01

标题与段落

用标题建立“现象—证据—根因—处理”的清晰层级。

Markdown 写法
# 风扇故障复盘

## 现象
服务器出现风扇低转速告警。

## 影响范围
涉及 2 台计算节点。
实际效果

建议：一篇案例只使用一个一级标题；正文模块使用二级标题。空一行会开始新段落，本工具同一段内的换行也会保留显示。

02

强调与行内代码

突出结论、风险和需要精确输入的命令或字段。

Markdown 写法
根因是 **风扇连接器松动**。

该结论仍需 *现场复核*。

检查字段 `Fan3Speed`。
实际效果

快捷键：选中文字后按 Ctrl+B（macOS 为 Command+B）可插入或取消粗体。代码、命令、日志字段建议使用反引号包裹。

03

无序与有序列表

无序列表适合并列证据，有序列表适合执行步骤。

Markdown 写法
- SEL 出现风扇告警
- BMC 页面转速低于阈值
- 现场听到异常噪声

1. 导出 BMC 日志
2. 核对固件版本
3. 检查风扇连接器
实际效果

建议：列表符号后保留一个空格。当前编辑器重点支持单层列表，复杂嵌套内容建议拆成多个小节。

04

引用与重要提示

用于标识原始告警、日志原文或必须注意的风险。

Markdown 写法
> 2026-07-30 08:16:21
> Fan 3 speed below lower critical threshold

> 操作前先确认业务已迁移。
实际效果

建议：引用必须保留时间、设备或日志来源。不要只写结论，要让后续维护人员能够追溯证据。

05

链接与分隔线

链接到受控知识来源，并用分隔线划分不同阶段。

Markdown 写法
[查看内部维护规范](https://example.com/runbook)

---

以下为处理完成后的验证记录。
实际效果

安全说明：当前只把 http/https 地址渲染为可点击链接。发布前请确认链接属于公司批准的知识库或工单系统。

06

多行代码与日志片段

三个反引号可完整保留多行命令、配置和日志格式。

Markdown 写法
```
ipmitool sdr type fan
Fan3 | 1200 RPM | ok
```
实际效果

发布前请脱敏：删除序列号、IP、账号、Token 和客户信息。日志较长时只保留能支撑结论的关键片段。

07

表格（GFM）

适合对比节点、时间、状态、责任人和下一步行动。

Markdown 写法
| 节点 | 告警 | 当前状态 | 责任人 |
| :--- | :--- | :---: | ---: |
| Node-01 | 风扇低转速 | 已恢复 | 张工 |
| Node-02 | 无 | 正常 | 李工 |
实际效果

第二行必须使用至少三个短横线；冒号控制左对齐、居中和右对齐。每一行的列数应保持一致。

下面是一份可直接复制并替换内容的专业案例骨架。

Markdown 写法
# [设备/故障名称] 维护案例

## 1. 问题背景
- 设备型号：
- BMC/BIOS 版本：
- 发生时间：
- 影响范围：

## 2. 故障现象
描述告警、业务影响和现场表现。

## 3. 关键证据
> 粘贴经过脱敏的关键日志，并标注时间和来源。

| 检查项 | 结果 | 结论 |
| :--- | :--- | :--- |
| SEL 日志 | Fan 3 告警 | 与现象一致 |
| 风扇转速 | 1200 RPM | 低于阈值 |

## 4. 根因分析
**确认根因：** 在此写清直接原因和判断依据。

## 5. 处理步骤
1. 完成业务迁移或风险隔离。
2. 执行硬件检查或部件更换。
3. 清除告警并重新验证。

## 6. 验证结果
记录恢复时间、指标和复测结果。

## 7. 后续行动
- 责任人：
- 计划完成时间：
- 防复发措施：
